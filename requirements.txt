## 1. Problem Understanding - Describe the problem your system solves.
System purpose: The system manages sign-ups for a single event by registering users up to a fixed capacity and automatically placing any additional users onto a waitlist that follows a first-come-first-served order.

Inputs to the system:
  - capacity (int): A whole number greater than or equal to zero passed in when the system is created. Negative values are rejected.
  - user_id (str): A non-empty string passed into register, cancel, and status operations that uniquely identifies a user. The same user_id cannot appear more than once in the system at any time.

Outputs produced by the system:
  - register(): Returns a UserStatus object with state "registered" or "waitlisted" with a 1-based position number.
  - cancel(): Returns nothing on success. Raises NotFound if the user does not exist.
  - status(): Returns a UserStatus object with state "registered", "waitlisted" with position, or "none".
  - snapshot(): Returns a dictionary containing capacity, ordered registered list, and ordered waitlist.

Primary goal of the system: To reliably manage event registrations and waitlist promotions automatically and deterministically without requiring any manual intervention from the user.
---

## 2. Assumptions - List assumptions about the environment, users, or inputs.

A1: All user_id values are non-empty strings, comparisons are case-sensitive meaning "User1" and "user1" are treated as different users, and the caller is responsible for passing clean valid strings.

A2: The capacity value is set once at initialization and does not change during the lifetime of the system.

A3: Operations are processed sequentially and the system does not need to handle true concurrency at the language level.

A4: A user who cancels and re-registers is treated as a brand new user with no memory of their previous state.

A5: Waitlist position is 1-based and is recalculated dynamically after every cancellation.

A6: The system is responsible for all conflict resolution and the caller never needs to resolve conflicts manually.

A7: A capacity of zero is a valid input and means all users will be waitlisted immediately.

A8: The order in which register() calls are processed determines waitlist and registration order.

A9: Negative capacity values are invalid and must be rejected with a ValueError at initialization.

---

## 3. Functional Requirements - Describe the main behaviors the system must perform.

FR1: The system shall accept a fixed capacity value upon initialization.

FR2: The system shall register users when the number of currently registered users is below capacity.

FR3: The system shall place users onto a waitlist when capacity is full.

FR4: The system shall maintain waitlist order using first-come-first-served ordering.

FR5: The system shall automatically promote the earliest waitlisted user when a registered user cancels.

FR6: The system shall prevent a user from registering if they are already registered or waitlisted.

FR7: The system shall allow a user to cancel their registration whether they are registered or waitlisted.

FR8: The system shall allow a user to query their current status at any time.

FR9: The system shall return a status of "registered", "waitlisted", or "none" for any status query. The only valid states are "registered", "waitlisted", and "none". When state is "waitlisted" a 1-based position must always be included.

FR10: The system shall return a 1-based waitlist position when a user is waitlisted.

FR11: The system shall ensure the number of registered users never exceeds capacity.

FR12: The system shall handle a capacity of zero by placing all users directly onto the waitlist.

FR13: The system shall allow a user to re-register after previously cancelling. A user who re-registers after cancelling is treated as a brand new user and joins the end of the waitlist if capacity is full.

FR14: The system shall allow a waitlisted user to cancel before being promoted.

FR15: The system shall remain in a consistent state after every operation. Promotion must happen atomically within the cancel operation and status queries must always reflect the post-operation state immediately.

FR16: The system shall never place a user in more than one state at the same time. A user cannot exist in both the registered list and the waitlist simultaneously under any operation sequence.

FR17: The system shall produce a deterministic outcome for identical sequences of operations.

FR18: The system shall raise an error when a cancellation is requested for a user not found in the system.

FR19: The system shall automatically resolve all conflicts and promotions without prompting the user for any input. [Derived from C1 - Jane]

FR20: The system shall return a reason whenever it rejects a user action such as a duplicate registration or a cancellation for a user that does not exist. [Derived from C4 - Mo]

FR21: The system shall never silently drop a request and must always return either a success status or an error for every operation. [Derived from C5 - Mo]

FR22: The system shall produce exactly one response per operation so the user is never sent duplicate or repeated messages. When a cancel triggers a promotion, no additional response is generated for the promoted user. The promoted user/'s new status is only visible via a subsequent status query. [Derived from C3 - Jane]

FR23: The system shall include an explanation when a user is promoted from the waitlist to registered so the user understands why their status changed. [Derived from C4 - Mo]

FR24: The system shall behave consistently across repeated boundary scenarios such as querying a user that has never interacted with the system. [Derived from C6 - Mo]

## 4. System Constraints - Constraints are conditions the system must always respect. Each constraint should reference the persona attribute it originates from.
C1: The system must automatically promote the earliest waitlisted user upon cancellation without requiring any user input.
Derived from persona attribute: Jane - Behavior: "User trusts the system to resolve conflicts automatically"

C2: The system must produce the same outcome for identical sequences of operations every time.
Derived from persona attribute: Jane - Need: "User expects predictable and stable ordering"

C3: The system must produce exactly one response per operation and never send duplicate status messages.
Derived from persona attribute: Jane - Pain Point: "User is frustrated by duplicate or repeated messages"

C4: The system must return a reason message whenever it rejects a user action such as a duplicate registration or a cancellation for a user not found.
Derived from persona attribute: Mo - Need: "User needs clear explanations when the system rejects an action"

C5: The system must always return either a success status or a raised error for every operation and must never silently do nothing.
Derived from persona attribute: Mo - Pain Point: "User is stressed by silent failures or dropped requests"

C6: The system must apply FIFO ordering consistently so identical inputs always produce the same waitlist order.
Derived from persona attribute: Mo - Need: "User needs deterministic behavior under ties or conflicting conditions"

C7: The system must handle edge cases such as capacity zero and unknown user queries by returning an explicit status rather than failing silently.
Derived from persona attribute: Mo - Need: "User expects explicit handling of edge cases instead of silent failure"

C8: The system must never prompt the user to manually resolve a conflict.
Derived from persona attribute: Jane - Behavior: "User prefers minimal interaction when making decisions"

## 5. Acceptance Criteria - Acceptance criteria define how system behavior will be verified.
AC1:
Given a system initialized with capacity 2 and 2 users already registered
When a third user attempts to register
Then the system returns a UserStatus with state "waitlisted" and position 1
Linked Constraint ID(s): C2, C6

AC2:
Given a system initialized with capacity 1 and 1 registered user and 1 waitlisted user
When the registered user cancels
Then the waitlisted user is automatically moved to registered without any user prompt
Linked Constraint ID(s): C1, C2

AC3:
Given a user that is already registered
When that same user attempts to register again
Then the system raises a DuplicateRequest error with a reason message
Linked Constraint ID(s): C4, C5

AC4:
Given a user that does not exist in the system
When a cancellation is requested for that user
Then the system raises a NotFound error with a reason message
Linked Constraint ID(s): C4, C5

AC5:
Given a system initialized with capacity 0
When any user attempts to register
Then the system returns a UserStatus with state "waitlisted" and position 1
Linked Constraint ID(s): C7

AC6:
Given a user that was previously registered and then cancelled
When that same user attempts to register again
Then the system registers or waitlists them as if they are a new user
Linked Constraint ID(s): C7

AC7:
Given a system with 3 waitlisted users in order A, B, C
When the same sequence of operations is repeated twice from an identical initial state
Then the promotion order is identical both times
Linked Constraint ID(s): C2, C6

AC8:
Given a user that has never interacted with the system
When a status query is made for that user
Then the system returns a UserStatus with state "none" and does not raise an error
Linked Constraint ID(s): C5, C7

## 6. Edge Cases - Describe unusual or boundary situations the system must handle.
EC1: Capacity is set to zero so every user that attempts to register is immediately placed on the waitlist.
Expected system behavior: The system returns UserStatus with state "waitlisted" and position 1 for the first user and increments position for each subsequent user.

EC2: A user attempts to register when they are already registered in the system.
Expected system behavior: The system raises a DuplicateRequest error with a non-empty reason message.

EC3: A user attempts to register when they are already on the waitlist.
Expected system behavior: The system raises a DuplicateRequest error with a non-empty reason message.

EC4: A cancellation is requested for a user that does not exist in the system.
Expected system behavior: The system raises a NotFound error with a non-empty reason message.

EC5: The system removes the user and all users behind them shift up by one position immediately and the updated positions are reflected in any subsequent status query.
Expected system behavior: The system removes the user and recalculates all remaining waitlist positions in FIFO order.

EC6: A user cancels and then attempts to re-register and must be treated as a new user with no memory of their previous state.
Expected system behavior: The system registers or waitlists the user as if they are interacting for the first time.

EC7: Multiple cancellations happen in sequence and each one must promote the correct next waitlisted user in FIFO order.
Expected system behavior: Each cancellation promotes exactly one user from the front of the waitlist in order.

EC8: A status query is made for a user that has never interacted with the system at all.
Expected system behavior: The system returns a UserStatus with state "none" without raising any error.
